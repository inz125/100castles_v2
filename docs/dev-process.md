# 開発プロセス

このドキュメント自体を開発対象として扱い、機能を 1 つ作るごとに振り返って更新する。

## 1. 基本サイクル（機能 1 つ分）

仕様を決める段階と実装する段階を分け、**仕様書を書いたところで一度止める**。利用者が仕様を確かめてから実装に進めるようにし、段階ごとに使うモデルを切り替えられるようにするため。

### 段階 A: 仕様（ここで止める）

1. **仕様確認**: `docs/spec.md` の該当 D-xx を確認する。曖昧な点はインタビューで決めて D-xx として追記する（変更は行を消さず取り消し線で残す）
2. **受け入れ条件を書く**: `docs/spec.md` の「6. 実装待ち」に、ユーザー視点の振る舞い（Given/When/Then）と実装の注意点を書く。会話の文脈を知らない別のモデルが、仕様書だけを読んで実装を始められる粒度にする
3. **コミットして止める**: 仕様書だけをコミット・push し、PR を作って決めた内容を利用者に報告する。**実装には進まない**。利用者が PR をマージし、実装の指示を出すまで待つ

### 段階 B: 実装（利用者の指示で始める）

1. **仕様を読む**: `docs/spec.md` の該当 D-xx と「6. 実装待ち」の受け入れ条件だけを根拠にする。足りない点があれば推測せず利用者に聞き、仕様書に追記する
2. **TDD**: 外側から内側へ。どの層も Red を確認してから実装する
   - 受け入れ条件を App のテスト（`src/App.test.tsx`。Testing Library で画面の操作から保存まで通す）で Red にする
   - ドメインロジックを単体テストで Red → Green → Refactor
   - Repository は共通の契約テスト（`*.contract.ts`）を先に足し、InMemory・localStorage の実装で通す
   - 画面の部品を Testing Library で Red → Green → Refactor
   - クラウド（Firestore の実装・セキュリティルール）はエミュレータのテストで確かめる
   - App のテストを Green にする
3. **見た目の確認**: 画面を変えたら、開発サーバを iPhone の大きさ（Playwright の `iPhone 13`）でライト・ダークの両方のスクリーンショットに撮って確かめる
4. **品質ゲート**: コミット前に `npm run verify`（整形・lint・型チェック・単体/コンポーネント・エミュレータ・ビルド）が成功すること。結果は終了コードで判断し、出力を grep した結果をコミットの条件にしない。CI（GitHub Actions）でも同じものを実行する
5. **仕様書の後始末**: 実装した項目を「6. 実装待ち」から消す（決定事項の D-xx は残す）。「3. 公開済みの機能」を更新する
6. **振り返り（KPT）**: 下の「改善履歴」に追記し、必要ならこのドキュメント・CLAUDE.md・CI を更新する
7. **PR を作る**: 実装・後始末・KPT を 1 つの PR にして利用者に報告する。CI が通ったことを確かめてから報告する。マージは利用者が行う
8. **公開後の確認**: マージすると公開される（`docs/deploy.md`）。利用者が実機（iPhone）で確かめ、問題があれば次の段階で直す

## 2. ローカル環境

```sh
npm ci
npm run dev            # 開発サーバ（http://localhost:5173/100castles_v2/）
npm run check          # 整形・lint・型チェック・単体/コンポーネントテスト
npm run test:emulator  # Firestore エミュレータを起動してクラウドのテストを流す（Java が必要）
npm run verify         # check + test:emulator + build（コミット前に必ず流す）
```

- エミュレータのテストは本物のプロジェクトに触れないよう、エミュレータ専用の `demo-castles` プロジェクトを使う。初回はエミュレータの jar を取得するので少し時間がかかる
- クラウドのコンテナ（Claude Code on the web）にも Java が入っていて、エミュレータのテストを流せる。Docker デーモンは起動できない（`sudo dockerd` は許可されない）ので、actionlint は CI に任せる
- クラウドのコンテナには Firebase のログイン情報がないので、ルールの公開はできない（`docs/deploy.md` の自動公開か、利用者の手元から）
- Playwright と Chromium はクラウドのコンテナに入っている。見た目の確認のスクリーンショットに使う（`require('playwright')`。`playwright install` はしない）
- プロセスを止めるときは `pkill -f` や `ps | grep` のパターンで探さない（実行中のシェル自身のコマンド行にも一致して止まる）。ポート番号から PID を特定する

## 3. テスト方針

| 層             | ツール                          | 対象                                                       | 方針                                                                                                 |
| -------------- | ------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 単体           | Vitest                          | ドメインロジック（進捗・制覇の判定、距離、共有コードなど） | 純粋関数として切り出し、最も厚く書く                                                                 |
| Repository     | Vitest（共通の契約テスト）      | 端末内・InMemory・クラウドの保存                           | 同じ契約テストをすべての実装で流し、差し替えても同じ振る舞いになることを確かめる                     |
| コンポーネント | Vitest + Testing Library        | 画面・部品の振る舞い                                       | ユーザー操作とアクセシブルな名前で検証する。実装詳細に依存しない                                     |
| App            | Vitest + Testing Library        | 受け入れ条件（画面の操作 → 保存 → 表示、共有、同期）       | InMemory の Repository とクラウドで、画面から保存・同期まで通す                                      |
| エミュレータ   | Vitest + Firestore エミュレータ | Firestore の実装・セキュリティルール                       | 新しい置き場所には「許される使い方」と「形の違うデータ・削除・一覧の取得ができない」テストを必ず書く |

- **外部との境界**: 保存（Repository）・クラウド（CloudBookStore）・現在地（LocationProvider）はインターフェースで切り、画面のテストは InMemory・フェイクで速く流す。本物の実装はエミュレータ・実機で確かめる
- **失敗の理由まで検証する**: エラーになることだけでなく、エラーの種類（`UnsupportedVersionError` など）や表示する文言まで確認する
- **時刻**: 「今日」は注入してテストする。テストは `TZ=Asia/Tokyo` で動かし、UTC とのずれによる日付の不具合を検出する
- **実行順**: 単体・コンポーネントのテストは毎回ランダムな順で流す（`sequence.shuffle`）。単独と全体で結果が変わったら、まずテスト同士の共有状態（localStorage・プロトタイプの差し替えなど）を疑う

## 4. ブランチ・コミット・マージ

- **段階ごとに PR を作り、こまめに main へマージする**。段階 A（仕様）と段階 B（実装）はそれぞれ 1 つの PR にする。ブランチを長く生かして複数の段階を溜めない
- **PR は自動で作る**。段階の終わり（仕様書の push、実装の push）に、利用者に聞かずに Claude が PR を作る
- **マージは利用者が行う**。Claude は PR を作り、CI が通ったことを確かめて報告するまで。Claude はマージしない（main へのマージで本番に公開されるため）
- 次の段階は、前の PR がマージされた最新の main から始める。マージ前の PR があるうちに別の段階を始めるときは、その PR に積まず、利用者に確認する
- Firestore のルールを変える PR は、ルールが公開されてから画面が公開される順になっていることを確かめる（`docs/deploy.md`）
- 1 コミット = 1 つの意味のある変更（Red/Green/Refactor を細かく刻んでもよい）
- コミットメッセージは日本語。先頭に種別（feat / test / fix / refactor / docs / chore / process）
